**Status:** Design only · **Priority:** P0 release-quality dependency  
**Predecessors:** CS-002D4.1 identity, CS-002D4.2 typed binding, CS-002D4.4 manifest, CS-002D4.5 scheduler — designs accepted  
**Transaction dependency:** CS-001C / CS-002D4.3 remains blocked  
**Parent:** [CS-002D.4 production integration design](../architecture/CS-002D4-production-integration-design.md)  
**Reported:** 2026-10-17  
**Implementation:** Not authorized in this ticket

## 1. Purpose and decision

Define the reproducible verification program required before production cross-sheet integration can be accepted. This document specifies gate ownership, exact result comparisons, environment capture, artifact retention, and failure classification. It does not execute or implement a harness.

**Decisions:**

1. The functional regression reference is the **historical 105 failing core test identities** recorded by accepted CS-002C. This set is reference-only. Do not rerun another capture and call it the new baseline; do not use the 138-failure CS-000F.4 inventory as a substitute.
2. Every comparison uses raw Jest JSON from the candidate run and an identity-level diff against the frozen 105 identities. Counts, suite totals, and formatted Jest summary status are supporting evidence only.
3. Any changed failure identity is a regression until individually reviewed and explained. No new failing identity is allowed for adoption. A previously failing identity may disappear only when its test remains present and executed and a linked fix resolves it without weakening/removing assertions.
4. All acceptance artifacts are retained durably with the exact command, exit code, source revision, environment, and SHA-256 checksums. `/tmp` is an execution scratch location, not the archive.
5. Known timing-sensitive benchmark tests are still executed and reported, but their current unstable thresholds do not gate deterministic correctness. Their measurements are reported separately with workload/hardware metadata. No benchmark may be silently skipped or filtered from the report.
6. CS-001C/D4.3 transaction gates remain **blocked/not met** until that contract is accepted and implemented. D4.6 cannot mark overall adoption complete by treating the blocked gate as N/A.

## 3. Reproducible comparison environment

### Required environment record

Every baseline comparison and gate run records:

- commit SHA, branch/ref, dirty/clean worktree status, and a patch or diff hash if the worktree is not clean;
- OS name/version/kernel, architecture, CPU model/core count, memory, and relevant power/virtualization/container conditions;
- browser/version for browser/XLSX UI scenarios (or `N/A` for Node-only gates);
- exact Node, npm, TypeScript, Jest, and package versions; `npm ls --depth=0` output is retained;
- SHA-256 of `package-lock.json`, Jest config files, relevant tsconfigs, and the frozen 105-reference inventory;
- install command/output (`npm ci` from the checked-in lockfile), exact test commands, working directory, environment variables, exit codes, stdout/stderr, and elapsed time;
- explicit test/suite counts, passed/failed/skipped/todo counts, runtime-error suites, and raw Jest JSON paths/checksums.

The comparison runtime is Node `24.22.0`, npm `11.19.1`, TypeScript `6.0.3`, and Jest version resolved from the checked-in lockfile. Do not compare an unpinned local dependency tree to a clean candidate. If the supported runtime changes, first produce a separately approved reference comparison; do not silently compare across runtimes.

### Paired source runs

For a claimed before/after implementation result, run the pre-change source and candidate source from clean, separate worktrees with the same lockfile, pinned runtime, machine class, configs, and commands. Use one dedicated isolated runner; do not run competing CPU/memory jobs concurrently during timed or memory-sensitive suites. The historical 105 reference remains a third, frozen identity set, not the pre-change worktree's newly observed count.

No baseline or gate command is run by this design document. The prior 105 result remains a reference and is not reset.

## 4. Functional regression gate: 105 failure identities

### Canonical identity key

Normalize every Jest assertion result to:

```text
<repo-relative testFilePath> :: <fullName>
```

Normalize path separators to `/`; preserve parameterized full names exactly. Do not include error message, stack, source line, duration, or Jest suite status in the identity key: those may vary without changing which assertion failed. If a suite contains duplicate identical full names, append a stable occurrence ordinal in Jest result order and flag the duplication for review.

The immutable reference set is the 105 core failures in the accepted CS-002C inventory, whose `failures[]` entries carry `suite` and `test` fields. Validate that the inventory records ticket `CS-002C`, the accepted run metadata, and exactly 105 unique core identities before comparison. Record the inventory SHA-256 in every run manifest. Do not include IO-XLSX identities in this set.

### Comparison output

Produce a machine-readable diff and human-readable summary with:

- `baselineOnly`: historical failure identities not failing now;
- `candidateOnly`: currently failing identities absent from the historical 105 set;
- `common`: identities failing in both;
- test inventory changes: added, removed, renamed, skipped, todo, or no-longer-discovered test identities;
- runtime errors, failed suites, assertion counts, and suite-level changes as supporting context.

| Result | Rule |
| --- | --- |
| Pass | `candidateOnly` is empty; all intended test identities are still discovered/executed; every identity in `baselineOnly` has a linked fix/ticket or is individually explained; no assertion was weakened, deleted, or newly skipped to produce the change; raw artifacts and environment record are complete. |
| Fail | Any unexplained candidate-only identity; missing/renamed/filtered baseline test without a reviewed identity mapping; new skip/todo/focused test marker; runtime crash; absent raw result; or artifact/config mismatch. |
| Review required | An identity changes because a test title/path intentionally changed, or a baseline failure is fixed. A reviewer must link the old/new identities, show assertion preservation, and approve the mapping. It is not automatically a regression pass based on counts. |

A result with 105 failed assertions is not automatically a pass; 106 is not the only failure condition. Identity deltas, test inventory integrity, and explanations determine status. Newly resolved failures are welcome only as evidence-backed fixes. Existing failures remaining are reported individually and keep their owning functional gates open.

### Candidate core command

Use a unique durable output path, for example:

```sh
PATH="$PINNED_NODE_BIN:$PATH" \
node ./node_modules/jest/bin/jest.js \
  --config packages/core/jest.config.cjs \
  --ci --runInBand --logHeapUsage --coverage=false --json \
  --outputFile="$ARTIFACT_DIR/core-jest.json"
```

Do not add a heap cap or other runtime flag to the core command unless the historical comparison command used it; any approved environment change must be applied identically to paired runs and recorded. Capture shell exit status even though a known-failing historical suite is expected to exit non-zero. Do not convert non-zero to success with `--passWithNoTests`, `|| true`, or count-only interpretation. The harness may treat expected baseline identities as accepted only for this regression-delta calculation; other feature/test gates still require their own pass criteria.

### Package command templates

These commands are future harness invocations; none was run for D4.6. Set `PINNED_NODE_BIN` to the installation containing Node `24.22.0`, and `ARTIFACT_DIR` to the durable per-run directory.

```sh
PATH="$PINNED_NODE_BIN:$PATH" node ./node_modules/jest/bin/jest.js \
  --config packages/core/jest.config.cjs \
  --ci --runInBand --logHeapUsage --coverage=false --json \

NODE_OPTIONS=--experimental-vm-modules \
PATH="$PINNED_NODE_BIN:$PATH" node ./node_modules/jest/bin/jest.js \

PATH="$PINNED_NODE_BIN:$PATH" npm run typecheck --workspace @cyber-sheet/core
PATH="$PINNED_NODE_BIN:$PATH" npm run build
```

The renderer-canvas config and browser Playwright suite are run as separate gates if the integration changes affect them; preserve their independent raw output and browser/runtime versions. The complete core command is the baseline-delta run; focused deterministic suites are additional gates and do not replace it.

## 5. Gate inventory and pass/fail rules

| Gate | Required evidence | Pass rule |
| --- | --- | --- |
| Functional regression | Raw core Jest JSON + exact historical-105 identity diff + test discovery inventory + pinned environment | Zero unexplained new failing identities; no missing/hidden test; each fixed identity reviewed with preserved assertions. |
| Dependency correctness | Tests for local point/range, qualified point/range, transitive propagation, local-to-cross-sheet chains, formula replacement/clear, rename/delete, volatile propagation, invalid coordinates | All deterministic assertions pass; exact one-based bounds; no duplicate ownership or cross-workbook edge contamination. |
| Cycle correctness | Local and cross-sheet SCCs, mixed-tier cycles, self-cell and self-inclusive range, independent branch, blocked descendant, cycle expansion/removal/recovery, deterministic diagnostics | Exactly true SCC members classified; disabled-iteration members commit `#CIRC!`; descendants are separately marked blocked/propagated; recovery clears obsolete cycle state; no recursion overflow. |
| Identity and migration | Persisted worksheet IDs, allocator high-water mark, O1 stale-ID rejection, pivot metadata migration, rename/delete/duplicate-name, clone/restore/import isolation | O1 stale ID resolves to undefined/invalid; IDs stable on rename/whole-workbook restore; import allocates fresh target IDs; no replacement sheet captures deleted bindings. |
| Binding semantics | Cell/range values/errors, `#REF!`/`#NAME?`, arrays, lazy thunks, entities, quoted names/escaped apostrophes, `ISFORMULA`, `FORMULATEXT` | Typed results preserved; cached precedent reads do not recurse; formula-inspection functions inspect bound references; malformed/unresolved/deleted distinctions match D4.2. |
| Transactions | Multi-sheet mutation, commit/rollback, patch inverse, recalc once, aggregate events, no transient cache/event publication on abort | **Blocked/not met until CS-001C/D4.3 accepted and implemented.** Then all atomicity/recovery assertions must pass. |
| Persistence | CSEX v1/v2 decoding, independent object/manifest versions, length/CRC corruption, duplicate IDs/names, sidecar digest/occurrence integrity, staged restore, formula rebinding, clone/import | All compatibility cases pass; invalid candidates reject before exposure; old live workbook remains unchanged; dirty formulas recalc before cache generation is called current. |
| Workers | FormulaValue fidelity (including nonnumeric/error/array/entity), result envelopes, current generation/formula/binding revision/task validation, out-of-order completion | Stale or foreign results are discarded without cache writes, dirty clears, or events; current matching result commits once. |
| XLSX interoperability | Full `packages/io-xlsx` Jest results plus named single-/multi-sheet import-export fixtures covering formulas, values, strings, ordering, and supported features | No new or unresolved failures in required supported fidelity cases; current package suite passes. Known historical fixture setup failures are classified separately and cannot mask production fidelity failures. |
| Performance and memory | Controlled fixed workloads, seeds, hardware/runtime, warm-up/sample protocol, heap/RSS, counts, latency distributions | Correctness always gates. Performance gate passes only against thresholds approved before measurement; absent approved thresholds, report results as informative and leave the performance gate open. |
| Repository hygiene | `npm run check:no-focused-tests`, build/typecheck, `git diff --check`, artifact manifest | No focused markers; build/typecheck pass; no whitespace errors; evidence complete. |

No gate is marked pass when its evidence is absent. A blocked dependency is reported as blocked, not passed or waived.

### Partial cache writes on failed generation

D4.5's incremental result commits and event buffering are separate guarantees. Before the scheduler gate can pass, its implementation contract must choose—jointly with D4.3—whether a failed generation restores the previous committed cache checkpoint, invalidates every partially written cache and restarts, or uses another explicit recovery rule. In every case, no intermediate values may be labeled current or published as a successful generation. The harness injects a deterministic evaluator/worker failure after at least one result commit, then checks cache validity, dirty ownership, next-generation recovery, and event suppression. Event suppression alone does not pass this case.

## 6. Known flaky/timing-sensitive test classification

Timing-sensitive outcomes must be classified using exact `testFilePath + fullName`, not broad suite exclusions. CS-000F.4 records a 5-second AlphaVantage throttle timeout and a 10k-operation memory-growth assertion whose pass/fail varied across full runs. The parent D4 design also calls out two timing-flaky benchmarks but does not name them in its gate table. Before harness implementation, create a reviewed registry that maps each named timing-sensitive test to its source assertion and category; do not guess by suite title or mark entire suites flaky.

Categories:

1. **Deterministic correctness:** ordinary pass/fail gate; retries cannot erase a failure.
2. **Timing-sensitive benchmark:** always run in the benchmark campaign and preserve every sample; current unstable thresholds are reported separately and do not decide deterministic correctness. Stable, pre-approved performance thresholds may become a separate gate later.
3. **Infrastructure failure:** runner crash, OOM, missing dependency, browser install failure, or corrupted artifact. Mark the run invalid/incomplete, preserve logs, fix environment, and rerun the same candidate; never classify infrastructure failure as a product pass.
4. **Known functional failure:** one of the historical 105 identities. It remains visible in raw output and comparison; it is not skipped or filtered.

For timing-sensitive items, record run-to-run distributions and failure/pass status, including the two known timing-flaky benchmarks, instead of deleting them from Jest config or CI. Do not increase timeouts or loosen assertions merely to make adoption green; such a change needs a focused ticket and evidence that test semantics remain valid.

## 7. Performance and memory campaign

Keep performance verification separate from deterministic correctness. Before collecting results, freeze workload definitions and acceptance thresholds in a ticket-reviewed plan. For each workload record:

- dataset dimensions, populated cells, formula count/depth/fan-out, local/qualified point and range edge counts, range area, number of sheets, mutation/edit shape, cycle count, and random seed;
- runtime and machine facts from §3, including CPU model/core count, physical memory, OS/kernel, Node flags, and whether the run is virtualized;
- warm-up count, measured repetitions (minimum 30 for timing distributions unless a reviewed protocol sets another count), median, p90/p95, min/max, and all raw samples;
- heap before/after, peak RSS, GC/exposed-GC policy, and whether values are bytes, MB, or another unit;
- evaluations scheduled/completed/discarded, dependency/index query counts, generation count, result correctness checksum, and benchmark command/exit status.

Do not derive thresholds after seeing the candidate's numbers. Do not gate on a single elapsed-time sample. Until approved thresholds and stable workload methodology exist, report measurements without pass/fail claims. The full Jest suite's timing assertions are not a substitute for this campaign.

## 8. Artifact retention and review packet

One immutable artifact directory per candidate run contains:

```text
run-manifest.json
source.patch (or clean-worktree marker)
environment.txt
commands.txt
core-jest.json
core.stdout.log
core.stderr.log
core-identity-diff.json
core-identity-diff.md
focused-jest.json (per focused suite group)
transactions-jest.json
persistence-jest.json
workers-jest.json
xlsx-jest.json
xlsx-fixtures/ (input/output workbook hashes and expected semantic summaries)
performance/ (workload definitions, raw samples, memory snapshots, summaries)
build-and-guard.log
SHA256SUMS
```

Do not fabricate missing files for unrun gates; record them as `not-run` or `blocked` in `run-manifest.json`. Retain raw machine-readable outputs alongside summaries. Store artifacts in durable CI/artifact storage or versioned engineering evidence with retention appropriate for release audits. Redact secrets from logs without rewriting test-result data. Preserve complete command output and exit codes.

The review packet includes a concise status table: gate, status (`pass`/`fail`/`blocked`/`not-run`), artifact link/checksum, owner, and unresolved identity/defect. A total pass count or green badge cannot substitute for this table.

## 10. Overall adoption decision and dependencies

**Adoption passes only if every unblocked gate passes and no required gate is silently waived.** The core functional run may remain non-zero solely for explained historical identities, but no candidate-only failure is allowed, and changed/missing identities require explicit review. Deterministic targeted dependency, cycle, binding, migration, persistence, worker, and XLSX gates must pass. Transaction status remains blocked until CS-001C/D4.3 is resolved; production adoption cannot proceed while it is blocked. Performance remains open until its protocol and thresholds are approved and measured.

The original nine-phase recovery roadmap remains governing. The accepted 105-failure reference remains unchanged and reference-only. This specification does not authorize production integration, baseline capture/reset, test execution, builds, browser runs, benchmarks, merges, or releases.
