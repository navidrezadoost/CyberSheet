# CS-002D4-R1 PKG-16D — Pivot integration migration gate

**Purpose:** Map the seven currently blocked legacy Pivot integration suites to the smallest legitimate future Workbook-owned test surface.
**Evidence basis:** PKG-11C lifecycle proposal, PKG-15C standalone/public-read boundary, and PKG-15D full Core diagnostic.
**Verification in this lane:** Source/report review only; no Jest run.
**Authorization:** No source, test, API, or contract change is authorized by this migration map.
**Overall CS-002D4-R1 acceptance:** WITHHELD.

## Current gate

PKG-15D's no-exclusion full Core diagnostic reports six compile-blocked suites and one fixture-setup-blocked suite. The six compile failures execute zero tests because fixtures refer to unavailable Workbook Pivot registry, snapshot-store, dependency/recompute internals, or mutation methods absent from the read-only `WorkbookSheetView`. The remaining suite has 18 setup failures: its shared fixture calls post-publication `Workbook.addSheet()`, which rejects before the intended assertions run. No executed assertion failures were reported in this seven-suite set.

This is a test/API reachability and lifecycle-fixture gate, not a demonstrated failure of Pivot calculation. Current public Workbook Pivot creation and deletion reject as unavailable; the registry, snapshot store, recompute engine, and related collaborators remain private. `getPivotSnapshot()` can read only an already registered Pivot. Initial sheets can be supplied through `Workbook.create({ sheets })`, and subsequent source writes use the authorized seven-operation transaction surface. The PKG-11C facade below is a proposal pending owner decisions; it is not current capability.

## Common migration prerequisites

The smallest proposed Workbook integration boundary is the PKG-11C narrow facade, not public mutable registry/store/group-state getters and not returning a mutable `Worksheet`. At minimum, an owner decision must authorize a same-Workbook source identity, first successful snapshot publication, detached snapshot/status observation, source invalidation after the existing seven-operation transaction, and a defined refresh/read policy. `createPivot()` is declared but unavailable today; its declaration does not itself authorize use. Post-publication `addSheet()` is not a migration workaround: source and output sheets must be created initially unless sheet lifecycle is separately approved.

The following dependencies stay explicit:

- **D3-06:** unresolved formula behavior when only a stale last-good Pivot snapshot exists. It blocks tests that claim formula/query results for stale Pivot data, especially the formula integration suite. It does not block numeric snapshot comparisons that avoid stale formula consumption.
- **Detached Error representation:** standalone component tests preserve Error identity through calculation, transform, store, and query. That does not establish a detached Workbook DTO. `workbook.ts`'s generic detachment traverses enumerable properties, while standard Error `name` and `message` are non-enumerable. Before testing Error-valued detached snapshots/status, the owner must choose a stable spreadsheet-error DTO or an immutable Error-compatible representation and define fields/compatibility. This is distinct from D3-06.
- **D3-05/status and refresh policy:** generation, stale/failure status, read coherence, and whether reads lazily refresh need their approved definitions. Do not substitute component `dirty` flags for public guarantees.
- **Other scope:** slicer update/clear, anchor/destination behavior, snapshot binary persistence, deletion, source-sheet lifecycle, and new events require their own explicit inclusion/approval if legacy assertions depend on them. No new D2 transaction operation or D5-05 Application forwarding is implied.

## Gate disposition

The seven suites are not ready for a mechanical fixture rewrite. Six currently fail to compile against the public owner-view/API boundary; one reaches setup and rejects unsupported post-publication sheet creation. PKG-15 standalone and component coverage provides useful calculation, snapshot-store, invalidation, query, and recovery evidence, but is not a substitute for Workbook-owned registration or lifecycle coverage.

Recommended next step: obtain the Workbook/API owner's scoped decision on the minimum Pivot facade and its refresh/status semantics; separately resolve D3-06 before formula assertions over stale results and the detached Error representation before Error DTO assertions. Then authorize per-suite migrations that preserve only the contractually supported intent, leaving internal collaborator checks in component tests. No suite is to be deleted, weakened, or made to pass through casts/private state. This report makes no API, contract, test, or production change and does not promote overall R1 acceptance.
