## Decision boundary

Authoritative contract D0-06 says existing mutation APIs are synchronous in many standalone paths, a FIFO queue across asynchronous work is naturally Promise-based, and the first Workbook mutation API must define compatibility/versioning before it is exposed. It also records that the current Workbook `mutationPort` rejects and has no working write compatibility contract. D0-04 and D0-05 resolve queue ownership and explicit-context nesting; they do not decide the public signature/version policy. The PKG-02A–G and PKG-16B records establish bounded contracts for seven operation behaviors. Those operation approvals do not, by themselves, approve the full public API shape, a package versioning policy, or each additional public helper symbol.

### Operation contracts versus API approval

PKG-02A and PKG-02B close bounded row-height and column-width behavior; PKG-02C–G and PKG-16B establish the seven-operation transaction/event behavior and enumerate remaining scope limits. These approvals support the seven operation families only. They do not resolve D0-06's question of exposing a working Workbook write API, whether its five legacy `never` methods become Promise-returning, whether `transact` and its context become root API, the stability of error/health symbols, or release/versioning requirements. Standalone Worksheet synchronous APIs remain distinct and unchanged by this proposal. Pivot lifecycle, comment deletion, a new eighth operation, Application forwarding, formula syntax/origin changes, and global D2-11 closure are excluded.

## C1 — legacy assertion

The base `packages/core/__tests__/workbook-owned-escape.test.ts` contains the named test `R1 mutation port has stable typed calls that reject before any write`. It asserts that each of the five current port methods throws synchronously and that the read-only view remains empty. The unfiltered PKG-19D candidate run failed this one assertion (one suite/test failure); the test was not edited. PKG-19C classified that narrow expectation as obsolete relative to later operation-specific packages, but also expressly preserved the broader D0-06 compatibility question. PKG-19E says the assertion remains unchanged and any migration must retain the owner-boundary and no-partial-write checks.

**Lane A disposition:** keep C1 unchanged and retain its unfiltered failure as visible evidence until an attributable D0-06 decision or existing explicit approval is located. The available records do not clearly authorize changing this historical assertion. If the owner approves public activation, a separate, minimal test migration may replace only the five synchronous-rejection expectations with authorized success/await behavior, retaining the frozen view, owner-boundary, and no-partial-write assertions; that migration still requires its own bounded execution authorization. Do not count a filtered run as satisfying C1.
