# P1-08BB Lane B — Framework ownership and failure propagation

## Current initializer ownership

All three current initializers hold the `Workbook` only in a local variable, obtain a `WorkbookSheetView`, and call `CanvasRenderer` before publishing framework state. None stores the `Workbook` on the service/composable/store or returns it from the initializer.

## Workbook and renderer cleanup surface

`Workbook` has a public `dispose(): void` at [`workbook.ts:515–526`](../../packages/core/src/workbook.ts:515). It disposes pivot invalidation subscriptions and clears pivot dependency, anchor, registry, and snapshot state. The framework initializers above do not retain or return their local Workbook reference, so their public failure results offer no direct Workbook handle on which to call this method. The returned `WorkbookSheetView` contract at [`workbook-access-types.ts:34–77`](../../packages/core/src/workbook-access-types.ts:34) has no `dispose` member. The concrete owner-backed view contains an internal resolver closure ([`WorkbookSheetView.ts:44–53`](../../packages/core/src/WorkbookSheetView.ts:44)); that implementation detail is not a documented disposal route and this review does not treat it as one.

`CanvasRenderer` has a public `dispose()` at [`CanvasRenderer.ts:620–654`](../../packages/renderer-canvas/src/CanvasRenderer.ts:620). It cancels scheduled work, disconnects its resize observer, removes event listeners, disposes the worksheet subscription, unsubscribes from the optional drawing layer, and removes its canvas. Its constructor appends the canvas at [`:542–546`](../../packages/renderer-canvas/src/CanvasRenderer.ts:542), then initializes resize observation and dimensions, installs DOM listeners, registers subscriptions, and calls `redraw()` ([`:549–617`](../../packages/renderer-canvas/src/CanvasRenderer.ts:549)). If construction throws, JavaScript does not return an instance to the framework caller; the initializers have no renderer handle with which to invoke `dispose()`.

These APIs establish that cleanup methods exist for retained successful instances. They do not establish automatic cleanup on constructor failure, nor that a partially constructed instance can be recovered by a caller. Whether particular failed-construction paths allocate listeners/subscriptions before throwing must be established by the real-renderer test lane, not inferred from the mocked BA tests.

## BA evidence boundary and limitations

The BA lane reports and tests confirm that the renderer mock throws after the real `Workbook.create()` call. Vue observes null worksheet/renderer refs and no canvas; Svelte observes only its initial null state and a rejected initializer; Angular observes rejection and no returned result/container canvas. Each lane then demonstrates a clean retry. The exact reports are [Vue](P1-08BA-lane-a-vue.md), [Svelte](P1-08BA-lane-b-svelte.md), and [Angular](P1-08BA-lane-c-angular.md); their focused tests replace/mock the renderer constructor.

Accordingly, BA shows framework publication isolation and retryability. It does not exercise real CanvasRenderer allocation or cleanup, observe the local Workbook after failure, or prove that the failed Workbook was disposed. The existing tests do not settle whether renderer failure occurs before resources, after canvas attachment, or after listener/subscription registration. No production or test changes were made in this lane; the coordinator's real-renderer lane must provide any such evidence.
