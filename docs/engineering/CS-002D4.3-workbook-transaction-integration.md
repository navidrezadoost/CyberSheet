# CS-002D4.3 — Workbook Transaction Integration Specification

**Status:** Design specification · ready for review · **Priority:** P0

**Reported:** 2026-10-17

**Predecessors:** CS-001C gap assessment and authoritative mutation journal contract accepted; D4.1, D4.2, D4.4, D4.5, and D4.6 designs accepted

**Implementation:** Not authorized

## 1. Purpose and boundary

This specification defines how the accepted CS-001C mutation contract integrates with a workbook owner, worksheet APIs, formula calculation generations, event publication, and worker adapters. It resolves the D4.3 design decisions at API and lifecycle level. It does not implement them or verify production behavior.

The design preserves these ownership boundaries:

- One workbook transaction owns one authoritative mutation journal across worksheet and workbook metadata changes.
- D4.5 owns dependency closure, formula task ordering, SCC handling, generation identity, and acceptance of calculation results.
- D4.4 owns staged persistence restore and workbook manifest validation.
- The transaction layer owns mutation staging, commit/abort, and the boundary between committed user input and calculation status.
- `WorksheetPatch` may represent supported undo/redo operations; it is not a complete transaction rollback image by assumption.

The source reconciliation uses the [CS-001C gap assessment](CS-001C-gap-assessment.md), [CS-001C journal contract](CS-001C-authoritative-mutation-journal-contract.md), and [worksheet mutation inventory](../architecture/CS-001C-mutation-inventory.md). This document does not change the frozen CS-002C 105-failure identity set, authorize the experimental coordinator, or authorize production implementation.

## 2. Concrete architecture decision: staged workbook state and capabilities

### 2.1 Why staging is required

The existing `Workbook.getSheet()` returns a mutable `Worksheet`. Callers can retain that object and read it or invoke a mutator without going back through the workbook. Buffering worksheet events cannot prevent those callers from reading in-place edits. Therefore, an in-place transaction plus event buffering cannot enforce CS-001C read isolation.

**Decision:** workbook-owned transactions mutate a private staged workbook state. The live committed workbook state remains unchanged until mutation commit. Transaction-scoped handles resolve only to the staged state and carry the transaction capability required to mutate it. Workbook sheet views outside the transaction are read-only owner-backed views that resolve by stable `WorksheetId` to the current committed state on every call.

The journal remains authoritative: all staged user mutations are write-ahead recorded in one journal. Staging is the isolation/abort mechanism, not another journal. A transaction abort discards its staged workbook state and journal; it does not replay inverse patches against the committed workbook. If staged-state discard or owner recovery fails, the owner enters `rollback-failed` as required by CS-001C.

### 2.2 Owner and published state

`Workbook` owns:

```text
WorkbookOwner
  committedState: WorkbookState
  activeTransaction: WorkbookTransaction | null
  calculationState: current | pending | stale | unavailable
  mutationJournal: one session for activeTransaction
  scheduler: D4.5 workbook scheduler
```

`WorkbookState` includes the sheet directory/order, stable IDs and allocator high-water mark, worksheet stores and local graph state, workbook-owned cross-sheet bindings/dependency records, pivot/reference metadata, and active-sheet selection. The committed state is published through an atomic state-reference swap; no view retains a direct mutable worksheet object as its backing identity.

The staged state begins as a transaction-owned copy-on-write candidate derived from the committed state. Unmodified sheets/stores may be shared only if their ownership layer guarantees immutability and copy-on-write before mutation. Mutation journal entries are written before each candidate-state write. Mutating committed objects through shared references is prohibited.

### 2.3 Capabilities and retained handles

Workbook-owned worksheet access has two distinct interfaces:

```ts
interface WorkbookSheetView {
  readonly id: WorksheetId;
  readonly name: string;
  readCell(address: Address): WorkbookCellRead;
  getCell(address: Address): Readonly<Cell> | undefined;
  // Other read-only worksheet queries only.
}

interface TransactionSheet {
  readonly id: WorksheetId;
  setCellValue(address: Address, value: CellValue): void;
  setCellFormula(address: Address, formula: string, cachedValue?: CellValue): void;
  // Explicitly eligible mutators only; see §5.
}
```

These are interface sketches, not API implementation. `Workbook.getSheet()` and equivalent public workbook lookups MUST return an owner-backed read-only view, not the internal `Worksheet`. `WorkbookTransaction.getSheet()` returns a transaction-scoped capability bound to that transaction ID and staged state. A capability is rejected after commit/abort and cannot be reused against another workbook or transaction.

Existing raw `Worksheet` APIs remain available for standalone sheets not adopted into a `Workbook`. Once a worksheet is workbook-owned, its raw mutators MUST reject calls without the active transaction capability before writing. Internal engine/scheduler writes use separate private capabilities. A retained `WorkbookSheetView` remains valid after transaction commit and resolves the newly committed state by ID; a retained transaction handle becomes invalid. A legacy raw `Worksheet` acquired before adoption becomes detached/read-only and MUST fail mutation after adoption. It cannot be silently forwarded to a new sheet or transaction.

This API boundary is an intentional compatibility change for workbook-owned sheets. Existing call sites that expect `getSheet()` to return a mutable `Worksheet` need migration to `workbook.transact(tx => tx.getSheet(id)...)`. The source inventory and package exports must be checked during implementation planning; design acceptance does not assert migration completeness.

## 3. API and lifecycle contract

### 3.1 Proposed API shape

```ts
type MutationResult<T> =
  | { status: 'committed'; transactionId: TransactionId; value: T;
      calculation: { status: 'current'; generation: CalculationGeneration } }
  | { status: 'committed'; transactionId: TransactionId; value: T;
      calculation: { status: 'stale'; generation: CalculationGeneration;
        error: CalculationFailure } };

workbook.transact<T>(
  callback: (tx: WorkbookTransaction) => T,
): Promise<MutationResult<T>>;
```

The callback is synchronous. A thenable return is rejected before mutation commit, and any work it started must be observed/settled before transaction capabilities are revoked. `transact()` returns a discriminated result so callers can distinguish a durable mutation from calculation success. A callback/journal/validation failure rejects with an abort result/error and guarantees that committed state is unchanged. A post-commit calculation failure resolves with `status: 'committed'` and `calculation.status: 'stale'`; it MUST NOT be reported as if the user mutation rolled back.

Standalone worksheet behavior remains outside this workbook transaction API. No implicit transaction is created by direct mutation of a workbook-owned raw `Worksheet`.

### 3.2 State machine

```text
IDLE
  └─ transact begins ─> MUTATING (private staged state, journal open)
       ├─ callback / validation failure ─> ABORTING ─> IDLE
       └─ journal validates + atomic state swap ─> MUTATION_COMMITTED
             ├─ generation accepted ─> IDLE / calculation current
             ├─ evaluation fails, cache checkpoint restored ─> IDLE / calculation stale
             └─ cache restoration fails ─> CALCULATION_UNAVAILABLE

Any failed staged rollback/discard ─> ROLLBACK_FAILED
```

`MUTATING` is workbook-exclusive. Nested `transact()` calls for the same workbook reject with a stable `TRANSACTION_ALREADY_OPEN` error before invoking the inner callback. Competing transactions for the same workbook serialize or reject; the contract chooses **reject while active** to keep ordering explicit. Separate workbook owners may transact independently.

Once the mutation state-reference swap occurs, abort is no longer a legal operation. Calculation failure follows §7 and leaves the mutation committed. A caller cannot interpret a thrown/failed calculation as a mutation abort.

### 3.3 Mutation transaction phases

1. Acquire the workbook transaction slot and pin the committed-state revision.
2. Create a staged candidate and open the one write-ahead journal session.
3. Execute the synchronous callback against transaction-scoped sheet/workbook handles.
4. Validate journal ownership, operation eligibility, identity constraints, formula/binding revisions, and all workbook invariants that can be checked before publication.
5. On failure, discard the staged state, close the journal as aborted, release capabilities, and leave committed state and public observers unchanged.
6. On success, atomically swap the committed-state pointer to the candidate, commit the journal, advance workbook revision, invalidate prior calculation work, and publish exactly one mutation commit envelope.
7. Start a D4.5 calculation generation using that committed mutation set. Return `current` after generation commit or `stale` after failure recovery completes.

No external read can observe candidate state before step 6. The transaction callback and its capability-bearing handles can observe their own staged writes.

## 4. One journal for sheets, workbook state, and patch operations

The journal is a single ordered stream, with records scoped by workbook and optionally by sheet. It captures:

- sheet cell content and complete cell metadata;
- local/qualified dependency registrations and volatile seeds affected by formula edits;
- styles, spills when user-authored, merges and any cells changed by merge operations;
- filters, validation, conditional formatting, protection, freeze panes, header/footer, dimensions, visibility, comments, icons, components, drawings, and supported structural changes;
- directory membership/order, active sheet, rename, sheet deletion/addition, allocator high-water mark, and associated pivot/reference metadata;
- patch application as ordinary journaled operations.

The record is captured before state mutation. For complex operations, one journal entry may hold a before-image of the entire affected region/store and its graph effects. The journal must not ask `onMutation()` after the fact to infer a missing before-state.

`TransactionContext` becomes a lifecycle compatibility adapter over this session. `PatchRecorder` either becomes the write-ahead journal implementation or a deterministic projection from it. `recordingApplyPatch()` may return an inverse patch for undo history, but its per-operation inverse list does not determine abort. `WorksheetPatch` projection must either represent all requested effects or reject the projection; it cannot report a partial patch as complete.

Journal sequencing is transaction-local and deterministic. For operations targeting different worksheets, order is the actual callback order. Journal entries carry stable IDs, never sheet display names as identity. The journal closes exactly once on commit/abort. The experimental workbook coordinator remains non-exported and has no journal authority.

## 5. Public API eligibility and restrictions

### 5.1 API routing rules

| Current API family | Workbook-owned behavior under this contract |
| --- | --- |
| `Workbook.getSheet`, `activeSheet`, worksheet name/id lookups | Return read-only owner-backed views. Reads resolve current committed state by `WorksheetId`. No mutators or mutable store access are exposed. |
| `Workbook.transact` / proposed `WorkbookTransaction` | Only public entry point for mutations of workbook-owned sheets and workbook metadata. Transaction handles expose the explicit eligible mutation surface. |
| `Worksheet.setCellValue`, `setCellFormula`, `clearCellContent`, `clearCellFormula`, `deleteCell`, style/merge/spill/filter/metadata/structure APIs | On a standalone `Worksheet`, retain standalone semantics. On a workbook-owned internal worksheet, raw calls without transaction or engine capability reject before write. Public callers use transaction handles. |
| `Worksheet.getCell`, `getCellValue`, `forEachNonEmptyCell`, `getDrawingLayer`, stores/maps/sets, formula/graph inspection | Not exposed as raw mutable workbook backing. Read-only views return immutable snapshots/iterators or owner-resolved values. Mutable `DrawingLayer` access is prohibited outside a transaction capability and its mutations are journaled. |
| `registerDependencies`, `clearDependencies`, `notifyChanged`, volatile/DAG methods, `applyCalculatedValue`, `applyFormulaResults`, `completeScheduledRecalculation`, `recalc`, `autoRecalculate`, `evaluateBatch` | Internal engine/scheduler-only operations. Public access is removed, made non-exported, or guarded by internal capabilities. Workbook callers cannot bypass the workbook scheduler or transaction journal. |
| `Worksheet.applySnapshot`, progressive-load methods, `Workbook.restore` | D4.4 staged restore/load boundary. Reject during an active normal transaction and swap a fully validated candidate only after complete restore succeeds. |
| `Workbook.addSheet`, `deleteSheet`, `renameSheet`, active-sheet setter, pivot/reference registry mutation | Routed through the transaction handle, with journal records for directory, identity, and metadata effects. Direct calls outside transaction either become an explicit one-operation `transact` wrapper or reject; no in-place path remains. |
| Worker RPC `setCellValue`, `applyPatch`, `begin/commit/rollbackTransaction`, `reset` | Adapt to workbook transaction ownership. Patch requests inside a transaction use the same journal. Reset aborts/discards only when replacing the whole workbook by explicit contract. RPC reads see committed views unless they are issued through the transaction capability channel. |

### 5.2 Initially unsupported operations

The system may defer transaction eligibility for a mutation family, but must reject it before the first write. The initial implementation SHOULD use this rule for structural row/column insertion/reordering, snapshot replacement, progressive loading, and any mutable drawing/store escape hatch until complete write-ahead records and restoration semantics exist.

For every public method in the mutation inventory, implementation planning must mark exactly one disposition: `journal-supported`, `transaction-only-internal`, `staged-restore-only`, or `rejected-before-write`. A generic event or an undocumented “best effort” path is not an allowed disposition. The source inventory must be updated as API changes land.

### 5.3 Read semantics

`WorkbookSheetView.readCell()` returns an explicit status-aware value, conceptually:

```ts
type WorkbookCellRead = {
  value: FormulaValue;
  formula?: string;
  calculation: 'current' | 'pending' | 'stale' | 'unavailable';
  generation?: CalculationGeneration;
};
```

The raw `Worksheet.getCellValue()` contract remains for standalone worksheets. Workbook APIs do not return a bare scalar while concealing whether it is stale. `getCell()` from a workbook view returns immutable metadata, not a mutable backing `Cell` reference.

During `MUTATING`, external workbook views read the previous committed revision. The transaction callback reads the staged candidate through its `tx` view. After mutation commit but before successful recalculation, direct status-aware reads may return the last accepted cache marked `pending`/`stale`; workbook formula binding and the scheduler MUST NOT treat that cache as current. If a formula has no previously accepted cache, its value is unavailable/stale rather than silently interpreted as a valid blank.

## 6. Abort, rollback, and identity behavior

### 6.1 Pre-commit abort

Because mutation occurs on staged state, abort is candidate disposal plus journal closure, not patch inversion against live state. The committed workbook revision, values, metadata, graphs, IDs, and observers remain unchanged. The transaction API revokes all transaction handles. If candidate disposal fails, mark `ROLLBACK_FAILED`, reject ordinary operations, and require reset or D4.4 staged restore. Never emit a successful abort if disposal did not complete.

If a mutation fails midway inside the candidate operation, its write-ahead record restores the candidate to a valid point before callback control continues or causes transaction abort. The operation must not leave an internally inconsistent candidate that can later be committed.

### 6.2 Allocator high-water mark

Worksheet IDs are allocated according to D4.1. Staged `addSheet` allocates from a monotonic workbook-owner allocator. If the transaction aborts, the sheet and directory membership disappear, but the allocator high-water mark remains advanced. IDs are never reused, even if the allocation had only been exposed within the transaction. Rename preserves the ID. Delete commit invalidates the deleted ID and its bound references; abort never causes another sheet to inherit it.

The allocator is the deliberate exception to logical-state rollback: transaction abort restores visible logical workbook state while preserving monotonic identity history.

### 6.3 Undo and redo

Undo/redo applies a new workbook transaction. The projected patch is validated before applying, each operation enters the same authoritative journal, and a failure aborts the staged candidate. Patch history may be cleared without affecting the active transaction journal. Patch formats that cannot represent full effects are not eligible for workbook-level atomic undo.

## 7. Calculation generation, cache checkpoint, stale reads, and retry

### 7.1 Boundary and owner

Mutation commit occurs at the atomic committed-state pointer swap. Calculation generation commit is a separate boundary. The D4.5 scheduler owns generation IDs, task freshness, SCC/blocked classification, and formula-result acceptance. The mutation journal owns no derived formula-result history.

Immediately before the generation can overwrite an output, the scheduler captures its checkpoint: prior cache existence and full `FormulaValue`, including errors, arrays, entities, lazy values where stored, and spill anchor/child state plus prior occupancy. Checkpoint capture precedes the first write and covers every output the generation could affect.

### 7.2 Successful generation

The scheduler commits results only when every required task and deterministic cycle disposition belongs to the current generation and matching formula/binding revisions. The generation status becomes `current`; its checkpoint is discarded; buffered formula-result events publish once in D4.5 order. Only then may dependent workbook formulas consume the generation’s result caches as committed/current.

### 7.3 Failed generation

If any evaluator/worker result fails after one or more cache writes:

1. Mark that generation failed and reject all subsequent late results from it before cache mutation or dirty clearing.
2. Restore every output and spill effect from the generation checkpoint, including deleting newly created caches/children where no prior result existed.
3. Keep the committed user mutations, formulas, bindings, and workbook revision. Keep the affected calculation closure dirty and set workbook calculation status to `stale` with the failed generation ID/reason.
4. Publish no formula-result events from that generation. Mutation commit has already been published; emit one calculation status/failure event.
5. Allow `retryCalculation()` (or the documented automatic retry trigger) to create a new generation over the same committed input revision. The retry must rebuild the required dirty closure and publish only after full generation acceptance.

While stale, `WorkbookSheetView` can expose the last accepted result with stale status, but `ReferenceBinder`, formula evaluation, and downstream scheduler tasks cannot consume it as a current precedent. Reads with no prior accepted value report unavailable rather than blank. Formula evaluation must not compensate by recursively calculating a precedent.

If checkpoint restoration fails, set `calculation-unavailable`; no binder or normal read can claim current values. Only diagnostic reads and explicit reset/staged restore remain available. D4.6’s failed-generation injection gate must verify this state transition after at least one cache and spill write.

### 7.4 Mutation while calculation is pending

The workbook serializes mutations and generations. A new `transact()` request while a generation is pending is rejected with a stable `CALCULATION_PENDING` status or queued by a future explicit API; this design chooses reject to avoid ambiguous view and checkpoint ownership. The caller retries after the generation becomes current or stale. On retry after stale, the new user transaction may commit while the old dirty closure remains pending, and its subsequent generation subsumes both mutation closures. The failed generation itself is never resumed.

## 8. Event publication and worker integration

### 8.1 Deterministic events

Raw worksheet events for workbook-owned sheets are internal signals and are not forwarded directly to external subscribers. The workbook event bridge buffers journal projections until mutation commit and derived formula events until calculation-generation commit.

The public ordering contract is reconciled with D4.5 as follows:

1. `mutationCommitted(transactionId, workbookRevision, affectedSheetIds, mutationSummary)` once, after the atomic state swap.
2. On successful calculation-generation commitment, publish the complete deterministic formula-result event batch.
3. Publish `calculationCommitted(generationId, workbookRevision)` as the final generation-completion notification, after the formula-result batch.
4. On calculation failure, publish `calculationFailed(generationId, workbookRevision, staleStatus)` only after checkpoint restoration completes. No result event from a failed generation is published.
5. No event from a failed transaction’s staged state is published.

Mutation events order by journal sequence. Derived events order by D4.5’s stable worksheet ID and cell-key order. A bridge must not emit both raw per-sheet events and the corresponding workbook event for one logical change. Event listeners run outside the mutation/scheduler critical section; their exceptions cannot roll back an already committed mutation or generation.

### 8.2 Worker protocol

Worker protocol needs an opaque workbook owner ID, transaction ID, workbook revision, calculation generation, and task identity. RPC request IDs remain correlation IDs only. A transaction begins against a pinned revision; requests must carry the transaction capability/ID; foreign or revoked IDs reject. Worker responses distinguish `aborted`, `committed/current`, `committed/stale`, and `unavailable`.

One worker may own one workbook transaction at a time. If a workbook is distributed across workers, one coordinator remains the sole journal owner; workers receive immutable staged task inputs and return generation-tagged results. They do not own mutation journals. The existing single-sheet `EngineWorkerHost` no-op `recalc(() => {})` is not formula-complete and cannot pass transaction calculation gates.

`reset` is an explicit whole-owner replacement operation. It revokes transactions/capabilities, disposes old state, and publishes a new owner revision only after replacement is complete. It cannot be used as a silent rollback workaround.

## 9. Acceptance gates and test design

All items below are design requirements, not executed tests. Tests must use stable identities, preserve assertion strength, contain no focused markers, and be retained under D4.6’s artifact protocol.

| Gate | Scenario | Required assertions |
| --- | --- | --- |
| Multi-sheet atomic commit | In one transaction, edit cells/formulas on two sheets and update workbook-owned metadata | Outside retained views remain on the committed revision until swap; after commit both sheets and metadata appear together; one ordered mutation event. |
| Retained handle isolation | Retain a sheet view before transaction; open a transaction and read/write through tx handle while querying the retained view | Retained view reads old committed state; raw worksheet mutation rejects; tx view sees staged state; after commit retained view resolves new state by ID. |
| Abort | Mutate several sheets, add/rename/delete sheet, then throw from callback | Committed workbook state and events unchanged; no commit event; all transaction handles revoked; ID allocation high-water mark does not rewind. |
| Eligibility rejection | Attempt each currently unsupported mutation family, including structural changes and snapshot replacement | Rejection occurs before the first write; staged candidate remains valid and can be aborted/committed without hidden side effects. |
| Complete journal rollback | Exercise every journal-supported mutation inventory row with before/after state and abort | Full worksheet/workbook state equality including formulas, metadata, spills, merges, dimensions, graphs, pivots, directory, and active sheet. |
| Patch path | Apply undo/redo patches inside multi-sheet transactions; inject invalid operation midway | Patch effects enter the one journal; failed apply aborts all sheets; inverse/redo preserves every projected field. |
| Rollback failure | Inject candidate discard/restore failure | `rollback-failed` state, no success event, reads/mutations reject except diagnostics/reset/staged restore. |
| Generation partial failure | Fail evaluation after at least one scalar, array/entity, and spill child write | Mutation stays committed; checkpoint restores all derived output and prior occupancy; affected formulas dirty/stale; no result events. |
| Stale reads and retry | Read after failed generation; retry successfully; inject late result from prior generation | Status marks prior values stale/unavailable; binder refuses stale cache; retry computes from committed inputs; late result cannot write/clear dirty/emit; successful results publish once. |
| Independent workbooks | Run transactions concurrently in separate workbooks with matching names/addresses | No shared journal, identity, cache checkpoint, event, or abort contamination. |
| Worker parity | Exercise same commit/abort/failure sequence via engine and worker | Identical externally visible statuses and state; RPC correlation ID cannot substitute for owner/transaction/revision/generation validation. |
| D4.6 regression gate | Run the authorized candidate functional comparison and transaction-specific suites when implementation is separately authorized | Frozen 105 identities remain reference-only; zero unexplained new identities; raw JSON, commands, environment, artifacts, checksums retained; transaction gates reported independently. |

## 10. Open implementation risks and decisions deferred to implementation review

- **Staging cost:** copy-on-write granularity and retained-state memory under large workbooks need measured workloads. The design does not authorize a benchmark campaign now.
- **Public API compatibility:** changing workbook lookups from mutable `Worksheet` to read-only owner-backed views requires a source/API migration inventory and semver decision.
- **Mutable escapes:** every nested object returned by reads—including styles, comments, drawings, maps/sets, and iterators—must be immutable or detached. A single mutable escape defeats read isolation.
- **State swap mechanics:** cross-sheet graph/binding stores, pivot metadata, and event bridges must share one commit revision so no consumer observes mixed revisions.
- **Cache checkpoint size:** arrays/entities and spill occupancy can be large. Checkpoint lifetime and storage representation require implementation profiling, without weakening completeness.
- **Error model:** exact public errors and diagnostics for rollback failure, stale reads, worker loss, and retry exhaustion need API review. Status distinctions specified here are normative.

## 11. Review boundary and next authorization

This specification completes the authorized D4.3 design stage and is ready for engineering review. Review should focus on the enforceability and compatibility of owner-backed read views, staging/checkpoint cost, failed-generation status-aware reads, and cross-sheet event ordering.

Design acceptance would close the D4.3 specification only. Production transaction implementation, verification harness changes, tests/builds/baseline runs, merge, and release still require separate authorization. The original nine-phase recovery plan remains governing; the 105-failure reference stays frozen; the experimental coordinator remains non-exported.
