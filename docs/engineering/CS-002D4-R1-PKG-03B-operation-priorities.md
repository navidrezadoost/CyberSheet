# CS-002D4-R1 PKG-03B — Operation Priorities

**Scope:** rank bounded candidates from unresolved D2-11 families. This is planning only; no operation is authorized by this document.
**Global D2-11:** UNRESOLVED. **Overall CS-002D4-R1:** WITHHELD.

## Ranking method

Candidates were compared on transactional safety (exact owner-state rollback), clarity of source ownership, rollback surface, API compatibility, event-contract dependency, deterministic testability, and architectural expansion risk. “Viable” means a finite operation can be specified against existing source owners; it does not mean implementation is approved or independent of all owner decisions.

## Candidates deferred from top three

| Family | Why it is not in the next three |
| --- | --- |
| Formula graph / volatile state | The current five cell operations already include graph Journal/Snapshot handling for the exercised slice. A separate volatile-state operation would require recalculation scheduler and formula-result lifecycle characterization first; this is not a single obvious next mutation kind. |
| Drawings | DrawingLayer object state and renderer image/resource lifecycle cross a broader set of ownership boundaries. A transaction would need to define resource acquisition/disposal, layer change events, and object identity. |
| Pivot accumulators/snapshots | Pivot state has its own invalidation/recompute engines, mutable group-state store, last-good snapshots, and D3 freshness policy. It is the broadest state coupling and should follow its own contract/integration readiness. |
| External host persistence | A Core in-memory transaction cannot guarantee atomic file replacement, host checkpoints, or durable rollback. Requires host/persistence-specific authorization. |
| Undo history | Workbook mutations currently provide FIFO commit/rollback but no Workbook-owned undo stack. History is a separate contract decision and would expand the API/retention model. |
| Structural insert/delete | Not a simple dimension write; remaps cells and multiple indexed stores. Handle as a separate composite operation after state-owner map and reference semantics are approved. |

## Next bounded implementation recommendation

Recommend a separate authorization for **transactional deletion of one comment**, with `deleteReplies` fixed to the current default `true` for the initial slice. Keep standalone `Worksheet.deleteComment` semantics and Workbook API additive. Do not add comment add/update, Application forwarding, history, persistence changes, or a generalized mutation framework. The exact candidate API, rollback design, and acceptance matrix are specified in the companion [design](CS-002D4-R1-PKG-03B-next-operation-design.md).

This recommendation is not formal authorization. D5-01 owner status remains pending per PKG-02G-D. A strict-order requirement, any new Application event requirement, or changed reply-deletion policy needs an owner decision and separately bounded revision before implementation.
